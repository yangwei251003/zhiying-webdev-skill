> 阶段三：tech_design 专用参考。产品设计完成后加载此文件。

## 一、技术架构方案设计规范（强制执行）

按以下顺序逐项设计，**每个设计项必须达到通过标准才进入下一项**。

| # | 设计项 | 通过标准 | 关键追问 |
|---|------|---------|---------|
| 1 | 前端技术选型 | 框架选择合理、组件库选择优质、技术栈易于落地 | "为什么选择这个框架而不是其他框架？有什么优势？" |
| 2 | 后端技术选型（如果需要） | 框架选择合理、数据库选择合适、架构易于维护 | "为什么选择这个数据库？能否支撑预期的数据量和访问量？" |
| 3 | 部署架构设计 | 服务器选择合理、CDN方案优化、监控方案完善 | "这个部署方案能否支撑预期的用户量和性能要求？" |
| 4 | 接口文档编写 | 所有接口详细说明、请求响应格式清晰、示例完整 | "接口文档是否足够清晰？开发人员能否直接使用？" |
| 5 | 开发计划制定 | 阶段划分明确、任务分解详细、时间节点合理 | "这个开发计划是否可行？有没有遗漏的任务？" |

## 二、前端技术选型规范

### 2.1 框架选择（必须说明理由）

**必须包含以下内容**：

1. **框架选择理由**：
   - 为什么选择这个框架（React/Vue/Angular等）
   - 框架的优势（性能、生态、学习曲线等）
   - 框架的劣势（需要克服的问题）
   - 框架的适用场景（为什么适合这个项目）

2. **框架版本选择**：
   - 选择的具体版本
   - 版本的稳定性
   - 版本的新特性是否需要

3. **框架配置方案**：
   - 路由方案（React Router/Vue Router等）
   - 状态管理方案（Redux/Vuex/MobX等）
   - 构建工具（Webpack/Vite等）

### 2.2 组件库选择（优先优质组件库）

**必须遵循以下原则**：

1. **优先使用优质组件库**：
   - Ant Design（React，企业级应用）
   - Material-UI（React，现代设计）
   - Chakra UI（React，简洁易用）
   - Element Plus（Vue，企业级应用）
   - Vuetify（Vue，Material Design）
   - Tailwind CSS（通用，高度可定制）

2. **组件库选择标准**：
   - 组件质量高（视觉效果好、交互体验好）
   - 组件数量多（覆盖常见需求）
   - 文档完善（易于学习和使用）
   - 社区活跃（问题能快速解决）
   - 维护稳定（版本更新及时）

3. **自定义组件开发**：
   - 只在组件库不满足时开发自定义组件
   - 自定义组件必须符合设计规范
   - 自定义组件必须可复用

### 2.3 其他前端技术选择

**必须包含以下内容**：

1. **CSS方案**：
   - CSS预处理器（Sass/Less/Stylus）
   - CSS-in-JS（styled-components/emotion）
   - CSS框架（Tailwind CSS/Bootstrap）

2. **动画方案**：
   - CSS动画（transition/animation）
   - JavaScript动画库（GSAP/Framer Motion）
   - 动画性能优化方案

3. **性能优化方案**：
   - 代码分割（Code Splitting）
   - 懒加载（Lazy Loading）
   - 缓存策略（Cache Strategy）
   - 图片优化（Image Optimization）

## 三、后端技术选型规范（如果需要）

**必须包含以下内容**：

1. **框架选择理由**：
   - 为什么选择这个框架（Express/Koa/NestJS/Django/Flask等）

   - 框架的劣势（需要克服的问题）

2. **框架配置方案**：
   - 路由方案
   - 中间件方案
   - 认证授权方案

### 3.2 数据库选择（必须说明理由）

**必须包含以下内容**：

1. **数据库选择理由**：
   - 为什么选择这个数据库（MySQL/PostgreSQL/MongoDB等）
   - 数据库的优势（性能、功能、成本等）
   - 数据库的劣势（需要克服的问题）
   - 数据库的适用场景（为什么适合这个项目）

2. **数据库设计**：
   - 数据表设计
   - 数据关系设计
   - 数据索引设计
   - 数据备份方案

**必须包含以下内容**：

1. **API风格选择**：
   - RESTful API（推荐）

## 四、部署架构设计规范

### 4.1 服务器选择

**必须包含以下内容**：

1. **服务器类型选择**：
   - 云服务器（AWS/Azure/阿里云/腾讯云）
   - VPS服务器（DigitalOcean/Vultr）
   - 物理服务器（自建机房）

2. **服务器配置选择**：
   - CPU配置（核心数、频率）
   - 内存配置（大小、类型）
   - 存储配置（大小、类型、速度）
   - 网络配置（带宽、延迟）

3. **服务器数量选择**：
   - 单服务器（小型项目）
   - 多服务器（中型项目）
   - 集群服务器（大型项目）

### 4.2 CDN方案设计

**必须包含以下内容**：

1. **CDN选择**：
   - CDN服务商（Cloudflare/AWS CloudFront/阿里云CDN）
   - CDN节点分布（全球/区域/本地）
   - CDN性能要求（延迟、带宽）

2. **CDN配置**：
   - 缓存策略（静态资源、动态内容）
   - 缓存时间（短期、中期、长期）
   - 缓存更新策略（主动更新、被动更新）

### 4.3 监控和日志方案

**必须包含以下内容**：

1. **性能监控**：
   - 监控工具（Google Analytics/New Relic/Prometheus）
   - 监控指标（加载速度、响应时间、错误率）
   - 监控告警（阈值设置、告警方式）

2. **日志管理**：
   - 日志收集（ELK Stack/Fluentd）
   - 日志存储（本地/云端）
   - 日志分析（实时分析、定期分析）

## 五、接口文档编写规范

### 5.1 接口文档必须包含的内容

**每个接口必须包含以下内容**：

1. **接口基本信息**：
   - 接口名称
   - 接口描述
   - 接口URL
   - 接口方法（GET/POST/PUT/DELETE）
   - 接口版本

2. **请求参数说明**：
   - 参数名称
   - 参数类型（String/Number/Boolean/Object/Array）
   - 参数是否必填
   - 参数默认值
   - 参数说明
   - 参数示例

3. **响应格式说明**：
   - 响应状态码（200/400/500等）
   - 响应数据格式（JSON/XML等）
   - 响应数据结构（字段说明）
   - 响应示例

4. **错误码定义**：
   - 错误码列表
   - 错误码含义
   - 错误处理建议

5. **接口调用示例**：
   - 请求示例（curl命令或代码示例）
   - 响应示例（实际响应数据）

### 5.2 接口文档格式规范

**必须遵循以下格式**：

```markdown
## 接口名称：[接口名称]

### 基本信息
- 接口描述：[接口功能描述]
- 接口URL：[接口地址]
- 接口方法：[HTTP方法]
- 接口版本：[版本号]

### 请求参数
| 参数名 | 类型 | 必填 | 默认值 | 说明 | 示例 |
|-------|------|------|--------|------|------|
| [参数名] | [类型] | [是/否] | [默认值] | [说明] | [示例] |

### 响应格式
```json
{
  "code": [状态码],
  "message": [响应消息],
  "data": {
    [响应数据结构]
  }
}
```

### 错误码
| 错误码 | 含义 | 处理建议 |
|-------|------|---------|
| [错误码] | [含义] | [处理建议] |

### 调用示例
```bash
curl -X [方法] "[URL]" -H "[Header]" -d "[Data]"
```
```

## 六、开发计划制定规范

### 6.1 阶段划分（必须明确）

**必须包含以下阶段**：

1. **前端开发阶段**：
   - 页面开发（按页面逐个开发）
   - 组件开发（按组件逐个开发）
   - 动画开发（按动画逐个开发）
   - 响应式开发（适配不同设备）

2. **后端开发阶段**（如果需要）：
   - API开发（按接口逐个开发）
   - 数据库开发（按表逐个开发）
   - 业务逻辑开发（按功能逐个开发）
   - 安全开发（认证授权等）

3. **联调测试阶段**：
   - 前后端联调（接口对接）
   - 功能测试（功能验证）
   - 性能测试（性能验证）
   - 兼容性测试（兼容性验证）

### 6.2 任务分解（必须详细）

**每个阶段必须分解为具体任务**：

1. **任务描述**：
   - 任务名称
   - 任务内容
   - 任务目标
   - 任务验收标准

2. **任务依赖**：
   - 任务前置依赖（必须先完成的任务）
   - 任务后置依赖（必须后完成的任务）
   - 任务并行依赖（可以并行完成的任务）

3. **任务时间**：
   - 任务预估时间（小时或天）
   - 任务开始时间
   - 任务结束时间
   - 任务缓冲时间（应对延期）

### 6.3 时间节点（必须合理）

**必须包含以下时间节点**：

1. **里程碑节点**：
   - 需求确认完成时间
   - 设计确认完成时间
   - 技术架构确认完成时间
   - 前端开发完成时间
   - 后端开发完成时间（如果需要）
   - 联调测试完成时间
   - 部署上线完成时间

2. **检查节点**：
   - 每周检查节点（每周检查进度）
   - 每阶段检查节点（每阶段检查质量）
   - 关键节点（关键任务的完成时间）

### 6.4 风险评估（必须包含）

**必须包含以下风险**：

1. **技术风险**：
   - 技术难点（可能遇到的技术问题）
   - 技术依赖（第三方依赖的风险）
   - 技术变更（技术栈变更的风险）

2. **时间风险**：
   - 时间延期（任务延期的风险）
   - 时间冲突（任务冲突的风险）
   - 时间不足（时间不够的风险）

3. **资源风险**：
   - 人员不足（开发人员不足的风险）
   - 资源缺失（图片等资源缺失的风险）
   - 资源质量（资源质量不达标的风险）

## 七、强制追问机制

用户反馈符合以下任一特征，**禁止接受并进入下一阶段**：

| 特征 | 反例 | 追问话术 |
|------|------|---------|
| 技术选型不明确 | "用React就行" | "为什么选择React而不是Vue？React有什么优势？有没有考虑其他框架？" |
| 数据库选择不合理 | "用MySQL就行" | "为什么选择MySQL？能否支撑预期的数据量和访问量？有没有考虑其他数据库？" |
| 接口设计不清晰 | "写个接口就行" | "接口的具体功能是什么？请求参数有哪些？响应格式是什么？有没有错误处理？" |
| 开发计划不详细 | "尽快开发就行" | "具体什么时候开始？什么时候结束？每个阶段需要多长时间？有没有缓冲时间？" |
| 风险评估缺失 | "应该没问题" | "有没有可能遇到的技术难点？有没有可能延期？有没有资源缺失的风险？" |

---

## 八、交互风格

1. 像专业的架构师，每次只展示一个技术方案
2. 给用户具体的技术对比（"方案A的优势"和"方案B的优势"对比）
3. 用户反馈不明确时主动提供多个技术方案供选择
4. 用户说"不知道用什么技术"时提供技术推荐和理由
5. 技术方案不合理时绝不敷衍，必须重新设计或调整
6. 善于总结、提炼技术要点
7. 每个技术方案完成后请用户确认签字
